## Typy, czas i historia

Wszystkie ID: Prisma `Int @id @default(autoincrement())`, SQL `INTEGER`, w TypeScript całkowite `number` w zakresie Prisma Int. Każdy FK ma ten sam typ. Kolumny z nazwami wielowyrazowymi mają `@map` do snake_case, cztery modele `@@map` do nazw tabel. Daty zdarzeń to `DateTime` (TypeScript `Date`, dokumentowane jako DATETIME w ERD); adapter SQLite ustali techniczną reprezentację w etapie 06.

`date` rezerwacji/blokady jest stringiem **lokalnego `YYYY-MM-DD` w `Europe/Warsaw`**, bez godziny i bez konwersji na północ UTC. API sprawdza faktyczne istnienie daty kalendarzowej; stały format pozwala porównywać lokalne daty. `createdAt` i nullable `cancelledAt` są znacznikami zdarzeń (instants, wymiana w UTC), a nie datami terminów. Porównanie przyszłości przelicza lokalne `date + startHour` na chwilę w Warszawie i wymaga `start > now`.

`startHour` jest całkowite w 7…22, `durationSlots` w {1,2}, `startHour + durationSlots ≤ 23`; tylko pon.–pt., bez wyjątków świątecznych. 45 min zajęć zajmuje 60 min siatki (1 slot, ostatni start 22:00), a 90 min zajmuje 120 min (2 sloty, ostatni start 21:00). Bufor jest częścią zajętości, nie dodatkową tabelą. Sąsiednie przedziały półotwarte nie kolidują.

Trwałe statusy to wyłącznie `ACTIVE`/`CANCELLED`. „Rozpoczęta”/„zakończona” są wyliczane z zegara (stan zajęć według długości 45/90 min; zajętość zachowuje cały bufor 60/120 min); nie zapisuje się `COMPLETED`. Anulowana nigdy nie blokuje terminu. Pola `cancelledAt`, `cancelledByUserId`, `cancelReason` są nullable: wszystkie null przy `ACTIVE`, wszystkie wymagane przy `CANCELLED`. Zbiór przyczyn to dokładnie `STUDENT_CANCELLED`, `ADMIN_CANCELLED`, `ROOM_DEACTIVATED`, `TIME_BLOCKED`.

`studentId` wskazuje właściciela-studenta, `createdByUserId` rzeczywistego inicjatora utworzenia (właściciela albo admina), `cancelledByUserId` rzeczywistego inicjatora anulowania. Przy blokadzie/dezaktywacji jest to administrator zatwierdzający operację. `TimeBlock.createdByUserId` wskazuje administratora tworzącego blokadę. Te trzy role User–Booking są oddzielnymi relacjami z parami nazw `BookingStudent`, `BookingCreatedBy`, `BookingCancelledBy` w Prisma.

## Co chroni baza, a co API

Szkic wymusza PK, NOT NULL, UNIQUE email/room_number i wszystkie FK. Każdy FK ma `onDelete: Restrict, onUpdate: Restrict`: brak kasowania kaskadowego historii, także dla opcjonalnego inicjatora anulowania. Zmiana danych sali nie zmienia jej ID. W etapie 06 połączenia SQLite muszą mieć włączone egzekwowanie FK. Indeksy `(room_id,date)` i `(student_id,date)` wspomagają odczyty, ale nie gwarantują braku przecięć.

API przed zapisem normalizuje numer sali: usuwa brzegowe białe znaki, scala ich ciągi do pojedynczej spacji i ustala jednolitą wielkość liter (wielkie litery); w `room_number` przechowywany jest wynik. Dzięki temu UNIQUE dotyczy wartości kanonicznej, bez dodatkowej kolumny. Email jest niepustym loginem, normalizowanym przez trim i małe litery przed zapisem/logowaniem, chronionym UNIQUE. Hasło przechowuje się wyłącznie jako bezpieczny hash; `display_name` nie jest sekretem ani identyfikatorem logowania.

Role, statusy i przyczyny są celowo `String`, bez założenia o zgodności enumów SQLite/Prisma. API waliduje zamknięte zbiory. **Etap 06:** wymagane CHECK dla role/status/cancel_reason, dodatniej całkowitej capacity, zakresów godzin/slotów i spójności trzech nullable pól anulowania; Prisma nie wyraża ich w tym szkicu, zatem należy uwzględnić je w ręcznie uzupełnionej migracji SQL i sprawdzić ich zachowanie. Żadnej migracji ani CHECK nie wdrożono w etapie 04.

W transakcji API musi sprawdzić autoryzację, role inicjatora/właściciela, aktywność sali przy rezerwacji, poprawność daty/dnia i przyszłość. Student ma lokalną datę ≤dzisiaj+14 **włącznie** oraz maks. trzy przyszłe aktywne po zapisie; count obejmuje także wpisy administratora, wyklucza rozpoczęte i anulowane. Administrator tworzący dla studenta omija **wyłącznie** horyzont i limit 3. Nie omija harmonogramu, przyszłości ani konfliktów właściciela/sali/blokad. Anulowanie studenta wymaga własności, ACTIVE i przyszłości; administrator też nie anuluje rozpoczętych/zakończonych.

Samo `UNIQUE(room_id,date,start_hour)` nie chroni 90-minutowych przedziałów: wpis 10:00 na 2 sloty przecina 11:00 na 1 slot mimo różnych startów. Nie chroni też jednego studenta przed równoległym zapisem w dwóch salach. Dlatego szkic nie używa takiego pozornego zabezpieczenia. Warunek przecięcia to `a.start < b.start + b.slots && b.start < a.start + a.slots`, dla tej samej daty oraz sali **lub studenta**; blokady sprawdza się dla sali.

Współbieżne zapisy wymagają jednego bezpiecznego odcinka SQLite: `BEGIN IMMEDIATE` przed odczytami, ponowna kontrola wszystkich reguł i zapis na tym samym połączeniu, jeden COMMIT/ROLLBACK. Sam podgląd, sama transakcja odroczona bez poprawnej obsługi konfliktów ani indeks startu nie gwarantują sukcesu. Szczegół integracji Prisma/adaptera musi zachować wspólny uchwyt `tx`; brak blokady oznacza 409 bez zapisu, inne błędy 500. Planowany **TC-11 musi sprawdzić prawdziwą SQLite**, również konflikt studenta między salami i przedziały 2-slotowe; nie wystarczy mock repozytorium.

Dezaktywacja sali i zakładanie blokady są atomowymi zmianami wielu rekordów. Najpierw podgląd i świadome potwierdzenie liczby anulowań (także zero), następnie ponowne ustalenie liczby i zestawu ID w transakcji. Różnica wymaga odmowy i nowej zgody; rozpoczęte, zakończone i CANCELLED nie wchodzą do zbioru. Dezaktywacja ustawia `isActive=false` i anuluje wszystkie przyszłe ACTIVE sali z `ROOM_DEACTIVATED`; blokada anuluje tylko przyszłe ACTIVE tej sali nachodzące na jej przedział z `TIME_BLOCKED`. Błąd cofa całą operację. Rekordów rezerwacji się nie usuwa. Reaktywacja/usunięcie blokady nie przywraca anulowanych; usunięcie samej blokady jest dopuszczalne w UC-07.

## Stan projektu

`erd.puml` i `schema-plan.prisma` są **projektem danych**, nie wdrożonym schematem. Aktualny [prisma/schema.prisma](../../prisma/schema.prisma) pozostaje technicznym szkieletem bez tabel biznesowych; migracje, seedy i rzeczywiste włączenie modeli nastąpią dopiero w etapie 06. Nie utworzono bazy, klienta ani dodatkowych modeli Session/Availability/RoomSlot/Holiday. URL pozostaje w istniejącym `prisma.config.ts`; szkic ma samodzielny datasource bez URL zgodnie z lokalną Prisma 7.

Walidacja lokalnym CLI `node_modules/.bin/prisma.cmd validate --schema docs/data-model/schema-plan.prisma` zakończyła się kodem 0 i komunikatem o poprawności wskazanego szkicu (Prisma 7.10.0, istniejący `prisma.config.ts`). Nie generowano klienta, nie uruchamiano migracji i nie łączono się z bazą. ERD nie został wyrenderowany: nie odnaleziono lokalnego renderera; brak SVG i weryfikacji wizualnej. Kontrola tekstowa obejmuje cztery tabele, sześć FK oraz zgodność pól/relacji z UML i Prisma; nie jest testem działającej bazy.
